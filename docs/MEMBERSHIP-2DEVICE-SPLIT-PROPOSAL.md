# 멤버십 키오스크 — 2대 분리(고객 태블릿 + 직원 노트북) 아키텍처 제안

> 상태: **제안 (2026-07-26) — 구현 전 지휘부·유저 검토.** 코드 미변경.
> 작성: membership 세션. 상위 정본: [MEMBERSHIP-KIOSK-SPEC.md](./MEMBERSHIP-KIOSK-SPEC.md). 선례: seat 위성(Supabase Realtime).

## 0. TL;DR — 권고 4개

```
① 뷰 분리 : 같은 위성 1개 앱, URL role 파라미터로 2뷰. 고객=?role=customer(기본), 직원=?role=staff.
② 연동    : ★연동(Realtime) 권고 — 직원 노트북이 드라이브 → 고객 태블릿 실시간 반영.
             단 각 뷰는 단독으로도 동작(연결 끊겨도 안 깨짐 = graceful degradation).
③ 페어링  : 매장 고정 룸(store id)을 URL/설정에 고정. QR·동적페어링 불필요(고정 단말).
④ DB영향 : 거의 없음 — Realtime 브로드캐스트(ephemeral)라 신규 테이블 불요. 프론트+채널인가 위주.
```

---

## 1. 뷰 분리 구조

- **같은 위성(apps/membership) 1개 앱**, 배포도 지금 그대로(gh-pages `/thinkmap/membership/`). 뷰만 역할로 분기.
- **URL 역할 파라미터**(라우터 신설 대신 경량):
  - 고객 태블릿: `/thinkmap/membership/`  (기본 = `role=customer`)
  - 직원 노트북: `/thinkmap/membership/?role=staff`  (또는 `#staff`)
  - ★gh-pages 정적 호스팅이라 `/staff` 딥패스는 404.html SPA 폴백이 필요 → **쿼리/해시 파라미터 권고**(서버 라우팅 불요, 북마크 1개로 고정).
- **컴포넌트 재사용**: 현행 3화면을 역할로 재배치(신규 최소).
  - 고객 뷰 = 기존 `CustomerSignupScreen` + 팝콘 참여/수령내역(StaffLookupScreen의 회원카드 부분 추출) — 거의 그대로.
  - 직원 뷰 = 기존 번호 조회 + `MemberListScreen`(검색) + 이벤트 트리거.
  - 현행 `MembershipKiosk`의 모드 토글 → **역할별 셸 2개**로 대체(고객 셸/직원 셸). 공용 컴포넌트는 그대로 import.
- 인증: 두 기기 모두 매장 계정으로 1회 로그인(§5.1 유지). 고객 태블릿도 store 세션 뒤에서 돈다(고객은 조작만).

## 2. ★핵심 결정 — 두 화면 연동 여부

| | (연동) Realtime 페어 ★권고 | (독립) 무동기화 |
|---|---|---|
| UX | 직원이 노트북서 회원 조회 → **고객 태블릿에 "안녕하세요 OOO님"+팝콘버튼 자동** | 고객은 태블릿서 셀프, 직원은 노트북서 따로 |
| 어르신 | ★직원이 드라이브(고객이 번호 입력 안 함) = 최적 | 고객이 직접 번호 입력(마찰) |
| 복잡도 | Realtime 채널+페어링+인가 필요(seat 선례로 낮음) | 없음(가장 단순) |
| 견고성 | 연결 끊기면? → **각 뷰 단독 동작 폴백** 설계로 방어 | 원래 독립이라 무관 |
| 신규 인프라 | Realtime 브로드캐스트(신규 테이블 X) | 없음 |

**→ 권고 = 연동(Realtime), 단 "연동 우선 + 단독 폴백".**
- 근거: 유저가 묘사한 시나리오("직원 조회 → 고객 화면에 인사말")가 곧 연동이다. 어르신 대응의 핵심이 "직원이 대신 조회 → 고객은 보고 터치만" = 연동일 때 성립. seat가 이미 같은 코드베이스에서 Realtime을 검증했다.
- **폴백 원칙**: 페어가 끊겨도 (a) 고객 태블릿은 셀프 가입/팝콘 가능, (b) 직원 노트북은 조회/리스트 가능. 연동은 "얹는 마법"이지 의존이 아니다 → 매장 운영이 절대 멈추지 않음.

**연동 데이터 흐름(브로드캐스트):**
```
[직원 노트북] 회원 조회 성공
   └─ Realtime broadcast(store 채널): { member_id, display_name(마스킹), today_event_claimed }  ← 최소 PII
        ▼
[고객 태블릿] 수신 → "안녕하세요 OOO님" + 팝콘 참여 버튼 표시
   └─ 고객이 팝콘 참여 터치 → claimEvent Edge(서버 1일1회) → 결과 broadcast → 양쪽 갱신
      (또는 직원이 노트북서 '수령확정' → 동일 Edge → 고객 태블릿 "참여 완료" 반영)
```
- ★고객 태블릿에 뜨는 건 **그 순간 카운터 앞의 그 회원 1명의 최소 정보**(마스킹 이름·오늘 팝콘 여부)뿐. 리스트·검색·타 회원은 고객 화면에 **절대 브로드캐스트 안 함**. 트랜잭션 종료/타임아웃 시 화면 클리어.

## 3. 기능 배치 (분리 + 큐 항목 재배치)

| 기능 | 고객 태블릿 | 직원 노트북 |
|---|---|---|
| 인사말("안녕하세요 OOO님") | ✅ (연동 시 직원 조회로 뜸 / 독립 시 셀프 조회 후) | — |
| 회원 가입(셀프/직원보조) | ✅ 가입폼(2단, 대형) | (직원이 대신 입력도 가능) |
| **이메일 없이 가입**(큐) | ✅ 이메일 optional + "이메일 없이 가입" 버튼 | — |
| **자동완성 차단**(큐) | ✅ 입력 필드 autocomplete off | ✅ 검색·입력 필드 |
| 팝콘 참여 버튼 + 수령내역 | ✅ 고객이 터치 / 내역 표시 | ✅ 직원이 '수령확정' 트리거 가능 |
| 번호 정확 조회 | (연동 시 불필요) | ✅ |
| **회원 리스트 검색**(성만·끝4자리·검색필수) | ❌ 절대 노출 안 함(PII) | ✅ 직원 전용 |
| 이벤트 관리/수령확정 | — | ✅ |

- 큐 항목(자동완성 차단·이메일 없이 가입·팝콘·회원리스트)은 **이 분리와 상충 없음** → 각 뷰의 해당 자리에 배치해 계속 진행 가능.
- 회원 리스트는 §5.2 보안 결정(성만+끝4자리 마스킹, 검색 필수)대로 **직원 뷰에만**.

## 4. 기기 페어링 방식 (연동 택 시)

- **권고 = 매장 고정 룸(store id)을 URL/설정에 고정.** 예: 두 기기 모두 `...?store=sarurufarm[&role=staff]`. 채널명 = store id.
  - 근거: "매장 고정 단말"이라 동적 페어링 불필요. 북마크 1회 세팅으로 영구 페어. 현재 1개 매장 = 단일 룸.
- QR·룸코드 입력은 **다매장·이동 단말**로 확장할 때의 옵션(지금은 과설계).
- ★**채널 인가(보안)**: Realtime 채널 구독은 **매장 계정(store) 세션 인증 필수** — 익명·외부 클라가 브로드캐스트를 엿듣지 못하게. Supabase Realtime을 인증 세션에 바인딩(익명 키로 임의 채널 조인 차단). 룸이 store id로 공개적이면 안 되고, 인증+채널 authorization으로 보호.

## 5. Edge/DB 영향

- **대부분 프론트 + Realtime.** 신규 마이그 **최소~없음**:
  - 연동 = Supabase Realtime **브로드캐스트(ephemeral)** → 상태를 DB에 저장 안 함 → **신규 테이블 불요.**
  - 팝콘 적립/조회/리스트 Edge는 앞선 제안(membership-history/list + crm 읽기 RPC)과 동일 — 그건 별도 게이트(SPEC §5.2·읽기RPC 제안). 2대 분리 자체는 그 위에 얹힘.
  - (선택) 연동 상태를 새로고침 후에도 복원하려면 작은 세션 테이블이 필요할 수 있으나 — 매장 상시 켜짐 + ephemeral로 충분 → **v1은 테이블 없이 브로드캐스트.**
- **채널 인가**만 보안 설계 필요(마이그 아닌 클라 인증 바인딩). RLS 신규 없음.
- 배포: 같은 위성·같은 URL(파라미터만) → **신규 배포 토폴로지 없음.** 기존 gh-pages 그대로.
- → **2대 분리에 걸리는 하드게이트 = 없음(프론트+Realtime).** 단 팝콘 수령내역/회원리스트의 crm 읽기 RPC·보안결정은 기존 게이트(§5.2) 유지.

---

## 6. 단계 제안 (승인 후)

1. 역할 셸 분리(고객/직원) + URL role 파라미터 — 프론트 리팩터(현 컴포넌트 재사용, 저위험).
2. 진행 중 큐(이메일 없이 가입·자동완성 차단) 각 뷰에 반영(상충 없음).
3. 연동 택 시: Realtime 브로드캐스트 페어(store 룸 + 세션 인증 채널) — seat 패턴 참고.
4. 팝콘/회원리스트 데이터는 기존 게이트(crm 읽기 RPC·보안결정) 풀리는 대로 배선.

> 결정 요청(유저): §2 연동 여부(권고=연동+폴백) · §4 페어링(권고=고정 store 룸) · §5.2 회원리스트 노출범위.
