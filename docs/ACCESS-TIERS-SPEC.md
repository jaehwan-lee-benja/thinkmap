> 상태: **Phase 0 합의 완료 (설계 확정, 구현 전)** · 작성 2026-06-25 · 브랜치 `feat/access-tiers`
> 관계: [ACCESS-MODEL.md](./ACCESS-MODEL.md)의 "단일 access 헬퍼 수렴(§4)"·"멤버십=L1 테넌시(§6)"를

## 0. TL;DR — 외울 것 딱 3개

```
① 테넌트 : 워크스페이스(조직) — 모든 데이터에 workspace_id
② 권한   : grant = (누가 , 어느 노드[조직 > 매장 > 항목] , 능력[소유자 > 편집 > 열람])
           · 기본은 deny. grant가 있어야 접근한다.
③ 판정   : can(user, target, 필요능력) 한 함수 + page_type 레지스트리(정책 = 데이터)
```

새 기능을 짤 때 외울 것은 **"노드 × 능력"** 둘뿐. 마스터/멤버/매장별 권한/항목 공유가
전부 이 한 규칙의 특수 경우다.

## 1. 배경 — 왜 새로 명명하나

ThinkMap은 한 조직의 운영 OS다(노트 + 업무일지·캘린더·배치도·급여·목표·자리후·재고).
권한 표현이 3 패러다임(A 소유공유 / B 공개 / C 마스터)으로 분화했고, page_type별 권한이
**SQL 정책 본문 · CHECK · 프론트 배열 · 산재 문자열 비교** 네 곳에 하드코딩돼 수동 동기 중이다.

이 문서는 그 셋을 **새 패러다임을 발명하지 않고** 하나의 모델로 *명명·수렴*한다. 목표는
"새 기능이 등급 이름만 고르면 RLS·UI가 정해지는" 상태. 동시에 향후 **다(多)매장·다(多)조직**
확장을 빅뱅 없이 흡수한다.

## 2. 핵심 모델

### 2.1 테넌트 = 워크스페이스(조직)

- `workspaces` 테이블 신설(1급). 모든 데이터 행은 `workspace_id`를 앵커로 갖는다.
- 오늘은 워크스페이스 1개(사루루팜). `is_master()`는 그 워크스페이스 마스터 판정의 얇은 shim.
- 완전히 별개의 회사 = **다른 워크스페이스**(미래). 한 사람이 워크스페이스마다 다른 등급일 수 있다.

### 2.2 노드 계층 — 조직 > 매장 > 항목

```
워크스페이스(조직)        ← 마스터(사장): 전 매장 + 마스터데이터 전부
   └ 그룹(매장 A, B…)     ← 멤버: 자기 매장 것
        └ 항목(개별 데이터) ← 특정인 개별 공유
```

- **매장 = 워크스페이스 아래 "그룹 노드"** (별도 워크스페이스 ❌). 한 사장이 전 매장을 함께
  관리·합산해야 하므로 테넌트로 쪼개지 않는다.
- 오늘은 노드 1개(조직)뿐 = 사실상 *조직 = 매장* → 멤버는 전부 편집(평평). `group_id`(매장)는
  컬럼 자리만 두고, 2호점 생기는 날 노드·grant를 row로 추가한다(구조 변경 없음).

### 2.3 grant = (주체, 노드, 능력)

권한 한 건 = **"누가(subject) / 어느 노드(scope) / 무엇을 할 수 있나(capability)"**.
기본은 **deny** — grant가 없으면 접근 불가.

### 2.4 능력 사다리 — 소유자 > 편집 > 열람

| 능력 | 뜻 |
|---|---|
| **소유자(owner)** | 전권. 민감/관리 데이터 포함, 타인 권한 부여 가능 |
| **편집(editor)** | 보고 고침 |
| **열람(viewer)** | 보기만 |

3룽에서 멈춘다(커스텀 역할·세분 권한은 YAGNI). 능력은 *값(데이터)*이라 나중에 스키마 변경
없이 추가 가능. 구글 드라이브 / GCP primitive roles와 동일한 어휘.

### 2.5 판정 — 단일 헬퍼 can()

```
can(user, target, 필요능력)
  = user가 target 자신, 또는 target이 속한 상위 노드(매장/조직)에 건
    grant 중 능력이 '필요능력' 이상인 게 하나라도 있나?

읽기 = can(user, x, 열람)   쓰기 = can(user, x, 편집)   민감/관리 = can(user, x, 소유자)
```

`is_master()` 등 기존 헬퍼는 이 함수의 얇은 껍데기로 남아 **오늘 동작 100% 동일**(워크스페이스
1개라 결과 같음). 성능·재귀는 `SECURITY DEFINER STABLE`로 회피(기존 패턴).

### 2.6 page_type 레지스트리 — 정책 = 데이터 (SSOT)

각 page_type이 자기 권한을 **한 곳(데이터)**에서 선언하고, RLS의 `can()`과 프론트 게이팅이
**둘 다 그걸 읽는다.** 새 page_type 추가 = 이 표에 **row 1줄**(정책 본문/CHECK/배열 4곳 수정 ❌).

| page_type | 기본 노드 | 읽기 요구능력 | 쓰기 요구능력 | 행가림 |
|---|---|---|---|---|
| `normal` | 항목(개인) | 열람 | 편집 | — |
| `daily`·`calendar` | 워크스페이스 | 열람 | 편집 | visibility |
| `members`(기본) | 워크스페이스 | 열람 | 소유자 | — |
| `payroll`·`goals`·`dashboard` | 워크스페이스 | 소유자 | 소유자 | — |
| `seat`·`inventory`(신규) | 워크스페이스 | 열람 | 편집 | (선택) |

> 구현 형태 = **(가) `page_type_access` DB 테이블** (결정). 규칙을 DB에 두고 RLS의 `can()`이 직접
> 읽는다(진짜 단일 출처). RLS 조회 비용은 `SECURITY DEFINER STABLE` 캐시로 회피.

### 2.7 데이터 소유 — 워크스페이스 자산 원칙

> **멤버가 업무로 만든 데이터는 그 멤버 개인이 아니라 워크스페이스(조직)가 소유한다.**
> 멤버가 떠나도 데이터는 고아가 되지 않고 조직 자산으로 남는다.

이 원칙은 두 조각으로 구현된다:

1. **귀속 = `workspace_id` 앵커.** 모든 데이터 행이 워크스페이스를 가리킨다 = "이 데이터는
   이 조직 것".
2. **접근 = grant, *만든 사람 아님*.** 워크스페이스 등급 데이터의 접근은 `can()`(워크스페이스
   grant)으로 정해진다. `user_id`(만든 사람)에 **의존하지 않는다**.

**`user_id`의 역할 재정의:**
- `user_id` = **`created_by`(누가 작성했나)** — 귀속/감사 용도로만 남긴다.
- **소유·접근은 절대 `created_by`에 의존하지 않는다** → `workspace_id` + grant 로만.
- 결과: 멤버 탈퇴/계정 삭제 시에도 데이터 보존, 다른 멤버·마스터가 계속 접근.

**자산 경계 — 모든 데이터가 워크스페이스 자산은 아니다:**

| 데이터 성격 | 등급(노드) | 자산 귀속 |
|---|---|---|
| 멤버의 **업무 내용** (daily·roster·seat·inventory·members …) | 워크스페이스 | **워크스페이스 소유** |
| **개인 메모** (normal 노트, 개인 goal 페이지) | 항목(개인) | **개인 소유**(자산 아님, 의도적) |

> 즉 "업무로 만든 건 조직 자산, 개인 메모는 개인 것". `page_type_access.default_scope`
> (`workspace` vs `resource`)가 이 경계를 데이터로 표현한다.

**일반화 — partner 케이스는 특례가 아니다.** §5의 `sarurufarm.partner` 데이터가 "워크스페이스
자산으로 남는다"는 것은, 이 원칙을 **모든 멤버에 적용한 한 사례**일 뿐이다. 따라서 §11의
"partner 데이터 귀속"은 기본값이 **워크스페이스 자산**(개인 메모 성격이 아닌 한)이다.

**시점:** Phase A 는 `workspace_id` 앵커(개념)만 박는다. "워크스페이스 소유"가 실제 발효되는
것은 Phase C 에서 라이브 정책을 `created_by` 기반 → `can()`(워크스페이스 grant) 기반으로
교체할 때다. 그 전까지 기존 테이블은 creator-owner 로 동작(무중단).

## 3. 주체 ↔ grant 매핑

| 주체 | grant 표현 | 닿는 것 |
|---|---|---|
| 워크스페이스 마스터(사장) | (조직 노드, **소유자**) | 전 매장 + 마스터 전용 전부 |
| 매장 점장(미래) | (매장 노드, **소유자**) | 그 매장 전권, 옆 매장 ❌ |
| 일반 멤버 | (매장/조직 노드, **편집**) | 그 범위 공유분 편집 |
| 읽기전용 멤버·감사자(미래) | (노드, **열람**) | 보기만 |
| 항목 개별 공유 | (항목, 편집/열람) | 그 항목만 |
| 가입 대기·비활성 | **grant 없음** (`status='pending'`) | 앱 진입 차단 |

미래 등급(관리멤버·손님 등)은 **칸 추가가 아니라 grant row 추가** — 확장이 데이터로 흡수된다.

가입 승인 흐름은 유지: 신규 = `pending` 자동 생성 → 마스터 승인 → `active` + grant 부여.
`active`가 아니면 `App.jsx`의 진입 게이트에서 차단(현행 그대로).

## 4. 기존 메커니즘 → 새 모델 (수렴표)

| 지금 흩어진 것 | 새 모델에서 |
|---|---|
| `is_master()` | (조직 노드, 소유자) grant |
| `worklog_board_members.role` | (매장/노드, 편집·소유자) |
| `shares`(viewer/editor) | (항목, 열람/편집) |
| `linked_accounts`(편집 임퍼소네이션) | (노드/항목, 편집) grant — §5 |
| `daily_blocks.visibility='master'` | "이 행은 읽기에 소유자 능력 필요"라는 리소스 쪽 요구 |
| `MASTER_ONLY_PAGE_TYPES` 등 page_type 분기 | page_type 레지스트리(§2.6) |

**물리 구현 = 단일 `grants` 테이블 (결정 B).** 마스터·멤버·항목공유·linked를 처음부터 하나의
`grants` 테이블로 통합한다(과도기 두 장부 ❌ — 부채·미래 합본 마이그 없음). 노드 계층(조직/매장/
항목)도 한 테이블에서 관리돼 멀티매장 미래가 깨끗하다. 비용은 **돌아가는 `shares`를 지금 이관**하는
것 하나뿐이며, §5의 무중단 규율(병행→검증→제거, 무삭제)로 안전하게 처리한다.

## 5. 임퍼소네이션 폐기 + 무중단 이관

임퍼소네이션은 "A가 B 데이터를 다룰 방법이 없어서" 만든 우회였다. grant가 그걸 정식 제공하므로
불필요해진다(= 모델 성숙 신호).

| 모드 | 처리 |
|---|---|
| **편집용**(`linked_accounts`) | **폐기** → grant로 대체. A는 자기 신분으로 처리(감사 추적 보존) |
| **뷰어모드**(마스터가 남 시점 열람) | 세션교체 메커니즘 폐기. 대신 **읽기전용 "권한 미리보기" = `can()` 시뮬레이션**으로 더 안전하게 유지 |

### 5.1 현재 실사용 — `rlawldus0621 → sarurufarm.partner` (editor)

- `sarurufarm.partner@gmail.com` = 멤버로 등록된 **공용 계정**(데이터 소유자).
- `rlawldus0621@gmail.com` = 실제 본인 계정. linked editor로 partner 데이터를 편집 중(다수 데이터).
- 즉 **현재 "일반 멤버 레벨" 자체가 공용 계정 + 임퍼소네이션 우회로 구현**돼 있다.

### 5.2 (a) 개인 계정 분리 + rlawldus0621 무중단 보장

선택: **(a)** 앞으로의 활동은 각자 본인 계정으로 기록(추적 가능). 과거 partner 데이터는
삭제·재배정 없이 **워크스페이스 자산(레거시)으로 보존**, 멤버가 grant로 계속 접근.

rlawldus0621은 **이미 본인 개인 계정**이라 분리할 것이 없다 — 계정 그대로 + (조직 노드, 편집)
grant만 받으면 끝. **무중단 이관 순서(반드시 이 순서):**

```
① workspaces·grant 셋업 + partner 데이터에 workspace_id 부여 (추가만, 기존 동작 그대로)
② rlawldus0621에 편집 grant + 조회를 "소유자 기준 → 워크스페이스 기준"으로 전환
③ rlawldus0621로 "데이터 다 보이고 편집됨" 실제 검증
④ 검증 끝난 뒤에야 linked_accounts / 임퍼소네이션 제거
```

> ⚠️ **위험:** 현재 코드가 `.eq('user_id', effectiveSession.user.id)`로 *소유자 기준* 조회를 한다.
> 임퍼소네이션만 떼고 ②를 안 하면 rlawldus0621의 user_id ≠ partner라 **데이터가 안 보인다.**
> 옛 경로(linked)는 새 경로가 검증되기 전엔 끊지 않는다(한 시점에도 둘 중 하나는 항상 작동).
> 데이터 삭제·재배정은 0.

## 6. 도메인별 등급 적용

| 도메인 | 노드/등급 | 읽기 | 쓰기 |
|---|---|---|---|
| 노트(pages normal)·schedule | 항목(개인) | 열람 grant | 편집 grant |
| 업무일지(daily/calendar)·daily_blocks | 워크스페이스 | 멤버 전원 | 멤버 전원(평평) + 행가림 visibility |
| 멤버 기본정보 | 워크스페이스 | 멤버 전원 | 마스터(소유자) |
| 급여·목표·대시보드 | 워크스페이스 | 마스터 | 마스터 |
| 배치도(roster)·**자리후(seat)** | 워크스페이스 | 멤버 전원 | 멤버 전원 |
| **재고(inventory) 품목 마스터** | 워크스페이스 | 멤버 전원 | 마스터(소유자) |
| **재고 입출고 기록** | 워크스페이스 | 멤버 전원 | 멤버 전원 |

> 자리후의 "역할 N종"은 **포지션(데이터 컬럼/프리셋)**이지 권한 등급이 아니다(MEMBER-SPEC의
> 보드멤버십 ≠ 인사역할 분리와 동일). 권한 차등이 필요하면 그때 grant 능력으로 표현.

## 7. 신규 기능 설계 가이드 — 계정·데이터·사람 3렌즈

새 기능을 짤 때 이 3묶음에 답하면 구조가 결정된다.

**① 계정(테넌시)** — 어느 워크스페이스? → `workspace_id` 앵커 필수. 계정 없는 주체는 기본 차단.
**② 데이터** — Documents(자유글) vs Structured(항목 row)? 소유/순서/soft delete/행가림 필요?
진입 페이지 있으면 → page_type 레지스트리에 한 줄.
**③ 사람(범위×능력)** — 읽기 요구능력 = 열람/소유자? 쓰기 = 편집/소유자? 노드 = 조직/매장/항목?
→ 곧 `can(user, target, 능력)`로 RLS·UI 동시 결정.

## 8. 일반 원칙 부합 (검토 결과)

| 결정 | 정설 | 부합 |
|---|---|---|
| 워크스페이스=테넌트 + workspace_id | 멀티테넌시(테넌시는 일찍, 소급은 재앙) | ✅ |
| grant=(주체,노드,능력) + 노드 계층 | 스코프드 RBAC(GCP IAM/K8s RoleBinding) | ✅ |
| 능력 3룽(소유자/편집/열람) | primitive roles(GCP·드라이브) | ✅ |
| grant 없으면 차단 | 최소권한 + 기본거부 | ✅ |
| 임퍼소네이션(편집) 폐기 → 본인+grant | 신분위장 안티패턴, 행위 귀속(감사) | ✅ |
| 뷰어 → 읽기전용 미리보기 | View-as는 읽기전용·감사로그 한정 | ✅ |
| 정책을 레지스트리(데이터)로 | 정책 외부화(OPA/IAM) | ✅ |
| 물리 통합은 멀티테넌트 때로 | YAGNI | ✅ |

큰 그림은 정설에 수렴. 빅뱅 없음.

## 9. 단계 로드맵 (무중단 점진)

```
지금(평평)      워크스페이스 1 + 노드 1(조직). 멤버 전원 편집. group_id 자리만.
   ↓            단일 grants 테이블(B) 신설. 신규 도메인(자리후·재고)부터 grant·workspace_id로.
   ↓            기존 shares·linked는 grants로 무중단 이관(§5 규율) 후 옛 경로 제거.
멀티매장        2호점 → 매장 노드 + (매장, 편집) grant 추가. 기존 변경 없이 row만.
   ↓
멀티테넌트      여러 조직 = 여러 워크스페이스. is_master() 본문을 워크스페이스-스코프로 교체.
```

## 10. 안전 가드

1. **authz 변경 = 데이터 노출 사고 후보.** 모든 RLS·헬퍼·정책 변경은 **SQL 제시 →
   supabase-guardian 검수 → 승인 → 통합 세션 적용**. 직접 적용 금지.
2. **무중단·무삭제.** 옛 경로는 새 경로 검증 전 제거 금지. 데이터 삭제·재배정 0.
3. **shim 보존.** `is_master()`를 얇은 껍데기로 남겨 본문만 격리 교체(전수 영향 차단).
4. **과도기 부채 명시.** 두 물리 테이블은 transitional로 라벨, 수렴 트리거(§9) 고정.
